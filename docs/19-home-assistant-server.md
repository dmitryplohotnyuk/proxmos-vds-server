# Вкладка Сервер В Home Assistant

## Развёрнуто 2026-10-11

В существующую пользовательскую панель добавлена вкладка
`http://192.168.0.222:8123/lovelace/server`. Предыдущие четыре вкладки сохранены.
Home Assistant Core 2026.10.1 один раз штатно перезапущен после проверки YAML;
финальное уточнение пакета применено через `rest.reload`.

Показатели:

- Один sensor мощности: `sensor.proxmox_rapl_power`, W, `state_class: measurement`.
  Это сумма независимых RAPL CPU package и dram, **не весь компьютер из розетки**.
  Вложенные core/uncore повторно не прибавляются. Подпись: «Мощность RAPL · CPU + память».
- История мощности за 6 часов, история и долгосрочная статистика штатного recorder.
- Число запущенных гостей и время последнего обновления.
- Автоматические списки VM и LXC: ID, имя, состояние Proxmox. Новые гости
  появляются без редактирования вкладки, шаблоны исключены; остановленные видны.
  Состояние `running` не доказывает работоспособность приложения внутри гостя.
- Отдельные ватты VM/LXC намеренно отсутствуют: надёжного измерения нет.
  Нет кнопок запуска/остановки, новых управляющих автоматизаций и MQTT-изменений.

## Передача Данных

На хосте systemd-служба `proxmox-ha-monitor.service`, только Python stdlib.
RAPL читается раз в 10 секунд, read-only инвентарь Proxmox через фиксированный
`pvesh get /cluster/resources --type vm` раз в 30 секунд. Запросы HTTP читают
кэш, не вызывают команды и не принимают параметры.

Endpoint `http://192.168.0.176:9120/metrics` привязан только к LAN-адресу.
Запросы разрешены с HA `192.168.0.222` и loopback (если интерфейс доступен),
требуется отдельный случайный bearer token. От другого LAN-клиента ответ 403;
от HA без корректного токена 401. Не публиковать порт через Cloudflare/роутер.
Это HTTP в доверенной LAN, не TLS: при недоверенной сети нужно шифрование.
Токен даёт только чтение этой телеметрии, не доступ к HA/Proxmox API.

Конфигурация хоста: `/etc/proxmox-ha-monitor.json`, root-only 0600.
Служба работает как root для чтения RAPL и локального Proxmox API; её filesystem
read-only, capabilities пустые, включены ограничения systemd, RAM max 256M.
CPUQuota=50% ограничивает пиковый CPU одним процессом, а не постоянную нагрузку.
При пробе `pvesh` тратил около 0.9 CPU-секунды на один опрос, то есть примерно
3% одного логического CPU при периоде 30 секунд, около 0.25% 12-поточного хоста.
Это ориентир конкретного замера, не гарантия будущей нагрузки.

HA штатно опрашивает REST раз в 15 секунд. При сетевой ошибке/таймауте сенсоры
недоступны; карточки не показывают старый список как актуальный. Если поток
сбора перестал обновлять кэш более 35 секунд, endpoint возвращает 503.
При ошибке инвентаря его сенсор недоступен, мощность может оставаться доступной.
При отсутствии/смене RAPL-зон мощность недоступна; ноль не подставляется.
Переполнение RAPL учитывается; после старта нужен второй замер.

## Повторная Установка

На Proxmox из копии этого репозитория:

```bash
bash scripts/install-proxmox-ha-monitor.sh 192.168.0.176 192.168.0.222
python3 scripts/install-ha-monitor-package.py --vmid 102
qm guest exec 102 -- ha core check
```

Второй скрипт рассчитан на HAOS с QEMU Guest Agent, контейнером `homeassistant`
и существующим mapping `homeassistant.packages` в configuration.yaml. Для другой
структуры скрипт откажет: объединить вручную, не заменять весь configuration.yaml.
Теги YAML разбираются структурным parser; другие includes и комментарии сохраняются.

Пакет: `/config/includes/proxmox_monitor/monitor.yaml`, секреты в `secrets.yaml`
в том же каталоге. Корневой configuration.yaml содержит только ссылку:

```yaml
homeassistant:
  packages:
    proxmox_monitor: !include includes/proxmox_monitor/monitor.yaml
```

Сохранить остальные пакеты. При первой установке после успешного `ha core check`
выполнить один штатный `ha core restart`. Если REST уже загружен, достаточно
действия `rest.reload` в инструментарии Home Assistant.

Установщик также копирует локальный frontend-файл
[proxmox-guests-card.js](../config/home-assistant/proxmox-guests-card.js) в
`/config/www/proxmox-guests-card.js`. В «Настройки -> Панели -> Ресурсы» добавить
`/local/proxmox-guests-card.js?v=20261011-1` как «Модуль JavaScript», затем обновить
страницу браузера. Повторно создавать ресурс при уже существующем URL не нужно.
При изменении JS увеличить версию URL для обновления browser cache. Это локальная
карточка по официальному Custom Card API, не скачанный компонент HACS.
В `/local` нельзя помещать секреты: файлы frontend доступны без авторизации.

Во вкладке редактора существующей пользовательской панели выбрать «Добавить вид»,
затем меню «Текстовый редактор» и вставить содержимое
[server_view.yaml](../config/home-assistant/server_view.yaml). Не заменять всю панель.
Если HA назначил иной entity_id из-за конфликта имён, уточнить три ссылки в view.

На новом хосте установщик создаёт новый токен; повторная установка пакета
передаст его HA. На текущем хосте токен не меняется. Изменение адресов требует
явного редактирования root-only конфигурации, перезапуска службы и обновления
пакета HA. URL/адрес источника не обновляются автоматически при смене подсети.

## Проверки И Откат

Первая резервная копия изменений: `/config/.proxmox-monitor-backup-20261011T153924Z/`.
Перед каждой установкой пакета создаётся новая закрытая копия configuration.yaml,
панели и предыдущего пакета/секретов. Это копия конфигурации, не всей БД HA.
Обычный полный HA backup включает конфигурацию и историю; ежедневный backup
управляющей части Domain Router эту VM и root-only monitor JSON не включает.
При пересоздании monitor JSON токен нужно передать HA повторно.

Проверено: `ha core check`, живые ватты, 6 LXC / 3 VM, динамические таблицы,
отказ доступа постороннему источнику, HTTP auth/path/stale-cache автотесты.
Живой тест остановки только службы мониторинга перевёл все три сенсора в
«Недоступно», таблицы в «Данные недоступны»; после старта данные восстановились.
Supervisor healthy/supported, Mosquitto и Zigbee2MQTT started. Гости не выключались.
Остановленное состояние гостя и изменение инвентаря покрыты модельными тестами;
специально останавливать рабочие VM для проверки не требовалось.

Финальный прогон: 105 автотестов прошли, проверка ссылок/шаблонов секретов и
Git-истории успешна. Содержимое JSON-объектов первых четырёх view не изменилось;
добавлен ровно один view. Проверены desktop и mobile 390 px без переполнения.
Рабочий процесс сборщика занимал около 11 MiB RAM между опросами, пик вместе
с кратковременным `pvesh` около 153 MiB; самопроизвольных рестартов службы нет.

Для отката удалить только view `server` через редактор HA, вернуть
configuration.yaml из первой копии (или удалить только include этого пакета,
если после копии были другие изменения), проверить `ha core check`, перезапустить
Core. На хосте `systemctl disable --now proxmox-ha-monitor.service`. Секреты
и backup удалять только после проверки отката. Исходный dashboard JSON не писать
в живой `.storage`: восстанавливать через редактор панели либо при остановленном Core.

Первоисточники: [RESTful](https://www.home-assistant.io/integrations/rest/),

[Dashboard views](https://www.home-assistant.io/dashboards/views/),

## Оформление Списков

Вместо узких markdown-таблиц используются две локальные `proxmox-guests-card`:
одна для `guest_type: lxc`, другая для `guest_type: vm`. Источник обеих -
`sensor.proxmox_inventory`; отдельных сущностей каждого гостя создавать не нужно.
Карточка использует штатные `ha-card`, `ha-icon` и цвета темы Home Assistant.

Строка содержит понятное имя сервиса, его собственную MDI-иконку, ID и исходное
имя гостя, статус с цветом и текстом. Для неизвестных новых узлов остаются исходное
имя и стандартная иконка VM/LXC. В заголовке число работающих узлов группы.
Статус running означает только состояние Proxmox, не application health.

Данные выводятся через `textContent`, не HTML-интерполяцию; нет внешних библиотек,
сетевых запросов, токенов и вызовов управляющих действий. Обновление идёт из
состояний HA, при unknown/unavailable старые строки скрываются. Изменения других
датчиков не приводят к повторному построению списка. Отключение карточки освобождает
подписку data context; legacy `hass` setter также поддерживается.

Проверки модели и DOM: `node --test tests/ha-guests-card.test.cjs`, включая новый
узел, все статусы, пустой список, XSS-подобное имя и потерю связи.
Локальная карточка подключена 2026-10-11; копия перед заменой оформления:
`/config/.proxmox-monitor-backup-20261011T164051Z/`. Проверены 6 LXC и 3 VM,
отрисовка всех иконок, обновление данных, desktop и mobile 390/320 px без
горизонтального переполнения строк. JSON остальных четырёх вкладок и первой
карточки с мощностью/историей совпадает с резервной копией. Передача телеметрии
не менялась; перезапуск Home Assistant для этой frontend-замены не потребовался.
Для возврата предыдущего оформления использовать редактор текущего view и его
резервную копию, не заменять остальные вкладки или всю живую `.storage`.

## SSD медиатеки — 2026-10-19

Под строкой Jellyfin (LXC 104) добавлены шкала заполнения, занятое и доступное
место. Источник — тот же API Proxmox: поле `media_storage`, переданное атрибутом
`sensor.proxmox_inventory`. Сборщик читает `statvfs('/mnt/media-ssd')` каждые
10 секунд, HA опрашивает API каждые 15 секунд. Это `/dev/sda1`, проброшенный
в контейнер как `/media/ssd`, а не его системный диск.

Объёмы показаны в десятичных ГБ. Резерв файловой системы указан отдельно;
процент равен `used / (used + available)`, как в `df`, без резерва.
При отсутствии точки монтирования API возвращает null, карточка показывает
«Нет данных о диске». При заполнении от 90% шкала становится жёлтой.

Резервные копии перед изменением: на Proxmox
`/usr/local/libexec/proxmox-ha-monitor.py.before-ssd-20261019`, в HA
`/config/.ha-media-ssd-20261019/` (карточка и пакет REST).
Ресурс карточки: `/local/proxmox-guests-card.js?v=20261019-ssd`.
Перезапущен только сборщик, пакет REST перезагружен без перезапуска HA.

Проверки: 3 unittest для статистики диска, 5 Node-тестов карточки,
валидная конфигурация HA, совпадение API со статистикой диска и отображение
в браузере. На момент проверки: занято 100,3 ГБ, доступно 122,9 ГБ,
резерв 12 ГБ, всего 235,2 ГБ; заполнение 44,9%.

### Отдельная карточка медиатеки

В тот же день показатели SSD вынесены из строки Jellyfin в самостоятельную
`custom:proxmox-storage-card`, зарегистрированную в том же JS-модуле.
Карточка находится в vertical-stack под виртуальными машинами. Крупный процент,
шкала и две колонки занятого/свободного места; резерв и общий объём внизу.
Источник API прежний. Ресурс: `?v=20261019-storage-card`.
Копия dashboard и JS перед переносом: `/config/.ha-ssd-layout-20261019/`.
Пять Node-тестов прошли, живое отображение проверено в браузере.
