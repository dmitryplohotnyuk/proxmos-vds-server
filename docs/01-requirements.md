# Requirements

## Цель

Создать LXC-контейнер в Proxmox, который будет единой точкой входа для доменов и будет прокидывать HTTP/HTTPS-запросы на нужные VM/LXC внутри локальной сети Proxmox.

Пользовательский сценарий:

1. Сервер подключается Ethernet-кабелем к интернету.
2. Контейнер сам держит исходящее соединение к внешнему входному слою.
3. Домены пользователя ведут на этот входной слой.
4. Внутри контейнера маршрут домена указывает на конкретный внутренний сервис.
5. VM/LXC с приложениями не знают, за NAT сервер или нет.

## Что должно работать

- Публикация HTTP/HTTPS-сервисов из внутренних VM/LXC.
- Работа за обычным роутером, NAT и CGNAT.
- Сохранение внутренних адресов VM/LXC при замене внешнего роутера и подсети.
- Автоматическое получение нового WAN-адреса и обновление DHCP-аренды.
- Добавление, изменение, отключение и удаление доменных маршрутов.
- Проксирование на разные внутренние адреса и порты.
- Разделение инфраструктуры и приложений: приложения живут в своих VM/LXC, маршрутизация отдельно.
- Возможность перенести публикацию с Cloudflare Tunnel на VPS/WireGuard без изменения приложений.

## Независимость от внешнего роутера

Внешняя сеть роутера и сеть приложений разделены:

```text
WAN/LAN роутера: DHCP, может изменяться
Внутренняя сеть Proxmox: 10.77.0.0/24, не изменяется
```

`domain-router` получает внешний адрес по DHCP, но обращается к приложениям по
постоянным адресам `10.77.0.x`. Контейнер также является NAT-шлюзом для этой
сети. Поэтому замена роутера не требует изменения доменных маршрутов или VM.

## Что не решает сам DNS

DNS только говорит клиенту, куда идти. Если сервер находится за CGNAT или входящие порты закрыты провайдером, DNS-запись `A`/`AAAA` не создаст входящий маршрут к домашнему серверу.

Поэтому для требования "работает вне зависимости от подключения" нужен один из вариантов:

- Cloudflare Tunnel.
- Собственный VPS с публичным IP и WireGuard-туннелем до дома.
- Другой внешний reverse proxy/tunnel provider.

Для первой версии выбран Cloudflare Tunnel, потому что он не требует белого IP и входящих портов на домашнем роутере.

## Критерии готовности первой версии

- Создан LXC `domain-router`.
- В LXC установлен и запущен Caddy.
- В LXC установлен и запущен cloudflared.
- Есть минимум один тестовый домен, который открывает сервис внутри Proxmox.
- Есть CLI-скрипт для управления маршрутами.
- Все маршруты описаны в одном конфигурационном файле.
- После изменения маршрута Caddy валидирует конфигурацию и перезагружается без остановки контейнера.
- Документация описывает восстановление после переустановки LXC.

## Не входит в первую версию

- Полноценная панель управления с авторизацией.
- Автоматическое управление DNS через Cloudflare API.
- Автоматическое создание VM/LXC приложений.
- Публикация не-HTTP протоколов. SSH/admin-доступ лучше делать через Tailscale или WireGuard, а не через публичные домены.

## Критерии готовности второй версии

Вторая версия добавляет приватную панель управления:

- панель доступна только внутри Tailscale и дополнительно защищена логином;
- CLI и панель работают с одним `routes.yml` без потери совместимости;
- конкурентные изменения маршрутов защищены файловой блокировкой;
- веб-процесс не работает от `root`;
- upstream ограничен разрешенной внутренней сетью;
- операции изменения маршрутов защищены сессией и CSRF token;
- действия администратора записываются в audit log;
- после перезагрузки LXC панель восстанавливается автоматически;
- публичный Cloudflare Tunnel не предоставляет доступ к панели.

Подробный объем и этапы: [`07-admin-panel-plan.md`](07-admin-panel-plan.md).
