# Как подключить домен к маршрутам

Актуальный Tunnel UUID и DNS Target доступны в разделе [Подключения → Cloudflare Tunnel](/integrations#cloudflare-tunnel). Инструкция не привязана к конкретному туннелю.

Схема нашей установки: **домен → Cloudflare → Tunnel → Caddy в domain-router → веб-сервис виртуалки**. Белый IP и проброс портов на роутере не нужны; серверу нужен работающий исходящий интернет. Эта инструкция предназначена для публичных веб-сайтов. SSH и закрытые сервисы остаются в Tailscale.

> Маршрут публикует веб-сервис в интернете. Авторизация в Domain Router защищает только саму админку, а не опубликованные сайты. Для закрытого сайта нужна собственная авторизация или отдельно настроенный Cloudflare Access.

## 1. Добавить зону в Cloudflare

1. Зарегистрируйте домен у любого регистратора, если его ещё нет.
2. Войдите **в тот же аккаунт Cloudflare, где находится наш Tunnel**. Откройте Domains → Add domain / Onboard a domain.
3. Введите корневой домен, например `example.com`, без `https://`, пути и поддомена `app`.
4. Выберите план Free, если платные функции не нужны. Проверьте импортированные DNS-записи. Сохраните записи почты: MX, TXT, SPF, DKIM и DMARC.

Уже активную зону повторно добавлять не нужно. Другой домен может использовать тот же Tunnel; отдельный туннель на каждую виртуалку не требуется.

## 2. Указать NS у регистратора

Cloudflare покажет назначенные зоне NS-серверы. В кабинете **регистратора домена** замените старые nameservers на эти значения. Не копируйте NS от другого домена и не создавайте их просто как DNS-записи в Cloudflare.

Если у регистратора включён DNSSEC для старого DNS-провайдера, сначала отключите его и удалите старую DS-запись. После активации зоны можно включить DNSSEC в Cloudflare и внести новый DS у регистратора. Для домена у Cloudflare Registrar ручная смена NS обычно не нужна.

Дождитесь статуса **Active** в Cloudflare. Обновление NS может занять до суток. [Официальная инструкция по зоне и NS](https://developers.cloudflare.com/dns/zone-setups/full-setup/setup/).

## 3. Направить DNS в наш Tunnel

Откройте нужную зону → **DNS → Records → Add record**. Для одного сайта `app.example.com` создайте:

| Поле | Значение |
| --- | --- |
| Type | CNAME |
| Name | `app` |
| Target | Скопируйте **DNS Target** из [Подключения → Cloudflare Tunnel](/integrations#cloudflare-tunnel) |
| Proxy status | Proxied, оранжевое облако |
| TTL | Auto |

В разделе **Подключения** значение DNS Target вычисляется из действующей конфигурации и копируется кнопкой рядом с ним. Формат: `<UUID>.cfargotunnel.com`. После замены туннеля используйте новый Target и вручную обновите соответствующие DNS-записи в Cloudflare. Не публикуйте credentials JSON, токены и `cert.pem`.

Для корневого сайта `example.com` используйте Name `@`. Для `www.example.com` добавьте отдельный CNAME с Name `www` и тем же Target. Если нужен DNS сразу для всех поддоменов первого уровня, можно вместо отдельных записей создать CNAME `*`; для самого корня запись `@` всё равно нужна. Явная запись поддомена имеет приоритет над wildcard.

Удаляйте или заменяйте только конфликтующие A/AAAA/CNAME **того имени, которое переводите в Tunnel**, предварительно сохранив старые значения. Не удаляйте чужие сайты, MX и TXT. В Target не указывайте `http://`, порт, LAN-IP, Tailscale IP или `10.77.0.x`.

DNS-запись сама по себе ещё не создаёт маршрут в Caddy. Наша админка также не меняет NS и DNS в Cloudflare. [Официальная документация DNS для Tunnel](https://developers.cloudflare.com/tunnel/concepts/routing/).

## 4. Разрешить новую зону на сервере

Для уже разрешённой зоны и её поддоменов пропустите этот шаг. **Новый корневой домен** нужно один раз добавить в серверный список разрешённых зон. Это действие администратора с root-доступом, не обычная настройка Cloudflare.

Выполняйте команды **внутри LXC domain-router**, не на Proxmox и не в целевой виртуалке. Сначала сохраните копии изменяемых файлов. Откройте `/etc/domain-router/environment` и сохраните все существующие настройки, добавив новую зону к `DOMAIN_ROUTER_ALLOWED_DOMAIN` через запятую. Например, для текущих зон и нового `example.com`:

```sh
DOMAIN_ROUTER_ALLOWED_DOMAIN=content-factory-vps.win,mesh-kremen.stream,content-factory.win,example.com
```

Этот файл должен принадлежать root и быть недоступен для записи пользователю веб-админки. Он загружается как shell-конфигурация: не вставляйте туда команды или непроверенный текст.

В старой установке CLI использует встроенный список, поэтому одного environment-файла недостаточно. Установите версионируемую root-обёртку, которая читает этот файл:

```sh
install -o root -g root -m 0755 \
  /opt/domain-router-ui/source/config/domain-router-wrapper \
  /usr/local/bin/domain-router
```

В `/etc/systemd/system/domain-router-ui.service.d/allowed-domains.conf` установите **такой же полный список** (создайте каталог и файл, если их нет):

```ini
[Service]
Environment="DOMAIN_ROUTER_ALLOWED_DOMAIN=content-factory-vps.win,mesh-kremen.stream,content-factory.win,example.com"
```

Затем примените изменения и проверьте, что старые маршруты остались доступны:

```sh
systemctl daemon-reload
systemctl restart domain-router-ui
domain-router list --json
domain-router status --json
```

Не заменяйте старые зоны только новой: это нарушит проверку существующих маршрутов. Для подключения новой зоны не запускайте повторно `configure-integrations.sh`: он предназначен для первоначальной интеграции и затрагивает настройки Tailscale. Сам Tunnel и его общий ingress `http://127.0.0.1:8080` менять не требуется.

## 5. Добавить маршрут в админке

1. Убедитесь, что веб-приложение установлено, запущено и слушает сетевой интерфейс, а не только `127.0.0.1` внутри виртуалки.
2. Во вкладке **Маршруты** нажмите **Добавить маршрут**.
3. Домен: `app.example.com`, без схемы и пути. Upstream: например, `http://10.77.0.10:80`. Используйте стабильный внутренний IP сервиса и его реальный порт.
4. Сохраните маршрут и убедитесь, что он включён. Кнопкой проверки проверьте доступность upstream.
5. Откройте `https://app.example.com` с внешнего устройства.

`example.com` и `www.example.com` являются разными именами. Для обоих нужны подходящие DNS-записи и два отдельных маршрута, даже если upstream одинаковый. Wildcard DNS не публикует все сервисы автоматически.

Переключатель во **Внутренних адресах** управляет доступом через Tailscale. Он не включает и не выключает публичный маршрут Cloudflare; для этого служит переключатель во вкладке Маршруты.

## 6. HTTPS и сертификаты

Для `https://app.example.com` **не нужен второй маршрут** на тот же домен. В Cloudflare → SSL/TLS → Edge Certificates проверьте, что Universal SSL активен. Стандартный сертификат покрывает корень и поддомены первого уровня; для `dev.app.example.com` может понадобиться отдельное решение для сертификата. Запись должна быть Proxied. [Ограничения Universal SSL](https://developers.cloudflare.com/ssl/edge-certificates/universal-ssl/limitations/).

В SSL/TLS → Overview можно оставить Automatic или выбрать Full (strict). Не переключайте в Flexible для исправления ошибок Tunnel: режим зоны не меняет локальный протокол. Cloudflare–Tunnel зашифрован отдельно; наш connector передаёт запрос в Caddy через HTTP на loopback. `http://10.77.0.10:80` означает HTTP на внутреннем участке Caddy–виртуалка. [Протоколы и TLS в Tunnel](https://developers.cloudflare.com/tunnel/troubleshooting/https-origins/).

Если требуется шифрование и внутри приватной сети, сначала настройте HTTPS с проверяемым сертификатом на самом приложении, затем измените upstream. Не указывайте `https://...:80` для HTTP-сервиса и не отключайте проверку сертификатов ради обхода ошибки.

Принудительный переход посетителей с HTTP на HTTPS можно настроить правилом для нужного hostname в Cloudflare. Опция Always Use HTTPS действует на всю зону: учитывайте остальные сайты. Приложение должно корректно учитывать заголовки обратного прокси, иначе возможен цикл редиректов.

## 7. Проверка и типичные ошибки

| Симптом | Что проверить |
| --- | --- |
| Cloudflare показывает Pending | Назначенные NS у регистратора, старую DS-запись, время обновления DNS |
| Домен не принимается админкой | Полный hostname без URL; корневая зона в разрешённом списке CLI и UI |
| DNS не находится или ведёт не туда | CNAME нужного имени, актуальный UUID, тот же аккаунт, отсутствие конфликтующей записи |
| 404 | Правильный hostname и включённый маршрут; затем проверить, не отвечает ли 404 само приложение |
| 502 / недоступен upstream | IP, порт, HTTP/HTTPS, запущенное приложение и firewall между domain-router и виртуалкой |
| Ошибка Tunnel | Состояние cloudflared, интернет на LXC, DNS Target и статус Tunnel в Cloudflare |
| Циклические редиректы | Настройки HTTPS приложения и доверие к заголовкам прокси; не пытаться лечить через Flexible |

Проверка из LXC domain-router для примера выше:

```sh
curl -I --max-time 10 http://10.77.0.10:80/
curl -I --max-time 10 -H 'Host: app.example.com' http://127.0.0.1:8080/
systemctl is-active caddy cloudflared
```

Проверка с вашего компьютера:

```sh
dig NS example.com +short
dig A app.example.com +short
curl -I --max-time 15 https://app.example.com/
```

При Proxied запрос `dig CNAME` может не показывать Tunnel Target: проверьте значение в Cloudflare DNS Records. Для существующего сайта учитывайте его ожидаемый ответ: редирект или запрос авторизации тоже может означать исправную связь. Не публикуйте Proxmox, SSH и административные панели без отдельной защиты.

## 8. Настроить Tunnel из админки

Откройте **Подключения → Cloudflare Tunnel → Настроить Tunnel**. Для изменения потребуется текущий пароль администратора и подтверждение операции.

**Credentials JSON** сохраняет нашу локально управляемую архитектуру. Загрузите credentials конкретного Tunnel, выданный командой `cloudflared tunnel create NAME`. Он содержит `AccountTag`, `TunnelID`, `TunnelSecret`. Не используйте аккаунтный `cert.pem` или API token. Новый Tunnel создаётся в Cloudflare отдельно; веб-панель подключает connector, но не создаёт аккаунт и не покупает домен. Локальный ingress автоматически направляется в Caddy `http://127.0.0.1:8080`.

**Connector token** предназначен для remotely-managed Tunnel. Создайте Cloudflared Tunnel в Cloudflare → Networking → Tunnels (в старом интерфейсе Zero Trust → Networks → Tunnels). Из команды установки скопируйте только token, не всю команду. В Cloudflare настройте published application routes для нужного корня и поддоменов с Service URL `http://127.0.0.1:8080`; имена должны совпадать с маршрутами Caddy. Для другого протокола или адреса этот профиль не предназначен. Нашу действующую локальную схему не переводите на remote тем же UUID: для миграции нужен отдельный новый Tunnel.

Перед заменой агент проверяет соединение отдельным connector. Затем сохраняет старую конфигурацию, запускает основной connector и проверяет его готовность. При ошибке возвращается старая конфигурация. Независимый таймер восстанавливает незавершённую замену через 90 секунд; если сервер перезагрузился во время операции, таймер восстановится при загрузке. Успешная проверка означает связь с Cloudflare, **не** исправность DNS, remote ingress или самого приложения.

После замены с новым UUID обновите CNAME доменов на актуальный DNS Target из Подключений и проверьте сайты. Кнопка возврата предыдущего Tunnel восстанавливает серверную конфигурацию, но не меняет DNS в Cloudflare. Токены не отображаются повторно и не сохраняются в браузерное хранилище или журнал админки. [Параметры token-file](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/run-parameters/).

## 9. Подключить Tailscale из админки

Во вкладке Подключения показаны два независимых узла: **Админка Domain Router** и **Шлюз приватных сервисов**. Первый обеспечивает HTTPS админки, второй открывает Jellyfin и другие внутренние сервисы.

Если узел требует входа, раскройте «Получить ссылку авторизации», подтвердите пароль и подключение. Затем нажмите «Авторизовать в Tailscale» и завершите вход в открытой вкладке провайдера. Страница состояния обновляется во время ожидания. Если требуется одобрение устройства или сетей шлюза, выполните его в консоли Tailscale. Показанные объявленные сети сами по себе не подтверждают, что маршруты уже одобрены.

Существующие параметры DNS, SSH и маршруты при восстановлении подключения сохраняются. На уже подключённом узле повторная авторизация не запускается. Для админки доступна отдельная операция восстановления Tailscale Serve на `127.0.0.1:8090`; она не сбрасывает остальные настройки через `serve reset`.

Выход из сети, смена аккаунта/tailnet, ACL и сроки действия ключей намеренно не управляются из этой панели. Смена tailnet может лишить вас доступа к самой админке. Такие операции выполняйте через SSH/консоль Proxmox с запасным доступом. Tailscale auth keys в этой реализации не требуются и не хранятся.

При развёртывании с нуля первое подключение самого domain-router выполняется из консоли/SSH: админка доступна только после появления защищённого канала Tailscale. Если этот канал уже не работает, веб-панель не сможет восстановить себя без другого канала управления. Используйте консоль CT 100 или SSH, затем `tailscale up` и `tailscale serve --bg http://127.0.0.1:8090`. Не запускайте `tailscale up --reset` на существующем узле. [Официальная документация Tailscale CLI](https://tailscale.com/docs/reference/tailscale-cli).
