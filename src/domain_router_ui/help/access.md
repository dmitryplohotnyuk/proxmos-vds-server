# Хранилище И Доступы

## 1. Первый Вход

Откройте хранилище кнопкой **Хранилище** в разделе [Доступы](/access).
На устройстве должен работать Tailscale с доступом к узлу Vaultwarden.
Если ещё нет аккаунта, администратор открывает регистрацию на 15 минут:
`pct exec 108 -- /usr/local/sbin/vaultwarden-registration open` на Proxmox.
Создайте аккаунт со своим email и отдельным длинным мастер-паролем.
Мастер-пароль не совпадает с паролями серверов и не передаётся Domain Router.
Регистрация автоматически закрывается после появления аккаунта либо тайм-аута.
Короткое окно регистрации доступно другим разрешённым ACL участникам tailnet;
проводите первичную настройку в доверенной сети и проверьте список аккаунтов.

В хранилище включите двухэтапный вход (например, приложение-аутентификатор).
Код восстановления сохраните вне этого сервера. SMTP пока не настроен:
письма, email-MFA и почтовое восстановление не используются. Потеря мастер-пароля
может сделать расшифровку данных невозможной.

## 2. Добавить Существующий Доступ

В Vaultwarden создайте запись типа **Логин**: название, адрес сервиса,
имя пользователя и известный пароль. Сохраните запись.
В её URL найдите UUID после `itemId=`; это идентификатор, не пароль.
В Domain Router откройте **Доступы**, нажмите плюс у нужного сервиса и заполните
логин, способ входа и **ID записи Vaultwarden**. Для аккаунтов Proxmox,
Cloudflare или Tailscale используйте внешнюю / ручную запись.

У ручной записи можно заполнить **Ручной узел**: название и IP вместе.
Такие записи группируются отдельно от автоматически обнаруженных гостей.
В каждой группе общий IP показан один раз; внутри находятся сервисы и аккаунты.

По умолчанию показаны сохранённые учётные записи. Фильтры **SSH-сервисы**, **Без привязки**
и **Все сервисы** позволяют проверить остальные обнаруженные точки входа.
Поиск работает по узлу, адресу, сервису и логину. У обнаруженного SSH-сервиса
с заполненным логином доступно копирование команды; пароля в ней нет.

Domain Router хранит только метаданные и ссылку. Наличие ссылки не подтверждает
существование записи или правильность пароля. Для нескольких пользователей одного
сервиса добавьте несколько учётных записей, выбрав тот же сервис.
Удаление привязки не удаляет запись из Vaultwarden и не меняет сервис.

## 3. Автоматический Список Сервисов

Список берётся из существующей инвентаризации, без передачи роутеру root-доступа.
Новые обнаруженные сервисы появляются без учётных записей. При исчезновении
сервиса сохранённая привязка остаётся с предупреждением. Повторно созданный
контейнер имеет другую identity и не наследует доступы старого контейнера.

Укажите **SSH-ключ**, **SSO / Tailscale** либо **Без пароля**, если это реальный
способ входа. Не разблокируйте root без отдельного решения владельца.

## 4. Автосохранение Новых Паролей

Используйте официальный Bitwarden CLI на доверенном устройстве. Выберите свой
сервер через `bw config server https://ИМЯ-ХРАНИЛИЩА.ts.net`, войдите через
`bw login` и временно разблокируйте CLI: `export BW_SESSION="$(bw unlock --raw)"`.
Никогда не сохраняйте эту переменную или мастер-пароль в systemd, `.env`, Git
либо логах. После операции выполните `bw lock` и `unset BW_SESSION`.

Сценарий `scripts/vault-save.py` сохраняет существующий или подготовленный пароль
через скрытый ввод либо stdin. Секрет не передаётся в аргументах процесса,
вывод содержит только UUID, название и логин. Проверяется выбранный HTTPS-сервер.
Сценарий не меняет пароли сервисов. При неопределённом результате сетевого запроса
сначала проверьте хранилище, чтобы повтор не создал дубликат.

Установщик новой VM `create-content-factory-vm.sh` поддерживает явное включение
`CONTENT_FACTORY_SAVE_TO_VAULT=1`, `VAULTWARDEN_URL` и временную `BW_SESSION`.
Он сохраняет пароль до создания VM; при отказе хранилища прекращает установку.
Пароль при этом не печатается, после создания выводится только UUID записи.
Это режим для доверенного оператора, не постоянно работающая серверная интеграция.
Существующие VM этим установщиком не изменяются. Остальные установщики пока
не подключены автоматически. Привязка UUID в Domain Router выполняется отдельно.

## 5. Клиенты И Аварийный Доступ

В расширении браузера или приложении Bitwarden выберите **Self-hosted** и укажите
тот же HTTPS-адрес хранилища. До отключения сервера синхронизируйте клиент.
Локальная копия позволяет читать ранее синхронизированные записи офлайн после
разблокировки; новые записи и изменения требуют доступного сервера.

Для SSH предпочтительны ключи. Менеджер паролей не заменяет SSH-настройки,
ACL Tailscale и учётные записи самих приложений. Единого входа во все сервисы
эта интеграция не создаёт.

## 6. Резервные Копии

При настроенном backup-recipient Proxmox ежедневно запускает зашифрованную age-копию.
Для согласованной копии БД и вложений Vaultwarden кратко останавливается.
На сервере находится только публичный ключ шифрования; приватный ключ нужен
для восстановления и хранится вне Proxmox. Это дополнение к мастер-паролю,
а не способ обойти шифрование записей.

Копия на Proxmox защищает от потери контейнера, но не от поломки физического диска.
Регулярно переносите её на другое устройство через `pull-vaultwarden-backups.sh`.
Инструкция восстановления и проверки: `docs/16-access-vault.md` в репозитории.
Настройки Domain Router и шлюза резервируются отдельно:
`docs/17-system-audit.md`. Сохранённая ссылка на запись не является backup пароля.
Автоматическая смена паролей сервисов намеренно не реализована.
